## 1. 产品定位与范围

- **一句话定位**：医学生（含医生）**院内信息撮合与联络平台**——信息汇总、分发、联络，实际行为（值班、指导）在线下发生。
- **核心场景**：
  1. 值班调班/换班：发布方发布待调时段并设置酬金，帮忙方接单替班；
  2. 病例指导：线下经验分享与学习交流；
  3. 简历指导：线下修改与咨询。
- **资金边界（红线）**：平台**不碰资金**。意向沟通与确认在线上完成，酬金由双方**线下点对点微信转账**，不经平台任何账户。任何代码路径不得出现平台代收转付（详见前期调研"二清"结论）。
- **验证期范围**：信息发布 + 匹配 + 站内私信 + 确认与互评；不做资金托管、不接支付。

## 2. 业务模型：双模式统一撮合

两种模式共用同一"撮合单 + 申请"模型，仅角色方向相反，数据层用 `dealings.type` 区分：

| 维度 | 需求单模式 `requirement` | 挂牌服务模式 `service` |
|---|---|---|
| 适用场景 | 换班/调班、病例求助 | 病例指导、简历指导（服务方主动挂牌） |
| 发起方 | 需方（发布时段+酬金+科室） | 供方（发布服务+定价） |
| 申请方 | 接单方（帮班/答疑） | 需求方（预约） |
| 确认方 | 发布方从候选人中选定 | 服务方接受预约 |
| 付款方向 | 发布方 → 接单方（线下 P2P） | 需求方 → 服务方（线下 P2P） |

## 3. 撮合流程与状态机

### 3.1 主流程

```
发布需求/挂牌 → 对方申请/预约 → 发布方/服务方确认锁定（开放站内私信）
→ 线下履约（值班/指导）→ 发布方确认履约完成 → 线下点对点转账酬金
→ 双方互评 → 信用分更新
```

### 3.2 撮合单状态机

| 状态 | 说明 | 迁移触发 |
|---|---|---|
| `published` 已发布 | 待申请 | 创建撮合单 |
| `applied` 申请中 | 候选人 ≥ 1 | 收到首个申请 |
| `confirmed` 已确认 | 双方锁定，开放私信 | 确认方选定候选人（其余申请自动拒绝） |
| `in_progress` 履约中 | 线下履约进行中 | 双方确认开始（或确认后 N 天自动进入） |
| `completed` 已完成 | 履约确认，待/已互评 | 确认方确认完成（超时自动确认） |
| `cancelled` 已取消 | 任一方在 confirmed 前取消 | 主动操作 / 到期无人接 |
| `disputed` 争议中 | 举报 → 平台仲裁 → 完结 | 任一环节举报 |

**超时规则**（防挂单，云函数定时任务实现）：
- 履约完成后 72h 未确认 → 提醒；96h 仍未确认 → 自动确认完成；
- published 超过 schedule 时段仍未 confirmed → 自动关闭。

## 4. 医院隔离模型（租户边界）

### 4.1 组织层级

```
省(province) → 市(city) → 医院(hospital)
```

- **医院是数据隔离的唯一边界**（租户），省/市仅用于注册时的级联选择与检索；
- 同院可见、可交互；**跨院不可发布、不可申请、不可私信**；
- 浏览策略（默认，待最终确认）：允许**切换医院透明浏览**列表（游客式查看），但一切写操作与私信严格限本院——便于 pilot 验收横向对比三家内容池。

### 4.2 隔离的强制实现（服务端，不信前端）

1. **所有数据读写走云函数**，云函数统一注入 `hospital_id` 过滤（取自用户档案，不取请求参数）；
2. **发布校验**：目标 hospital_id 必须 == 用户认证医院，否则拒绝；
3. **申请校验**：申请方与撮合单双方 hospital_id 必须一致；
4. **私信校验**：会话双方 hospital_id 必须一致且会话必须源于已确认撮合单；
5. 云数据库**安全规则兜底**（`doc.hospital_id == auth 所属医院`），双保险。

### 4.3 注册认证流程

```
微信一键登录(openid) → 选择 省→市→医院 → 提交认证材料(学生证/工牌/执业证照片)
→ 人工审核 → 绑定 hospital_id → 解锁发布/申请/私信
```

- 未认证：可浏览所选医院列表（只读），不可发布、申请、私信；
- 换绑医院需重新提交认证审核（防止跳院绕过隔离）。

## 5. 系统架构

```
┌─────────────────────────────────────────────┐
│ 微信小程序客户端（原生 WXML/WXSS/JS）          │
│ 首页(发现/搜索/筛选) · 发布 · 消息 · 我的      │
└──────────────┬──────────────────────────────┘
               │ wx.cloud.callFunction（免域名白名单）
┌──────────────▼──────────────────────────────┐
│ 微信云开发 CloudBase                          │
│ ├ 云函数：login / hospital / dealing /        │
│ │   application / message / review / report / │
│ │   admin(审核后台) / timer(超时任务)          │
│ ├ 云数据库：dealings / applications / users … │
│ └ 云存储：认证材料、举报证据                   │
├──────────────────────────────────────────────┤
│ 微信开放能力：订阅消息 · msgSecCheck/imgSecCheck │
└─────────────────────────────────────────────┘
```

技术选型依据见前期调研文档第六节。要点：免服务器、免域名备案、云调用直连微信开放接口。

## 6. 数据模型（云数据库集合字典）

| 集合 | 关键字段 | 说明 |
|---|---|---|
| `hospitals` | `_id, province, city, name, status(active/disabled)` | 医院（租户）注册表，运营后台维护 |
| `users` | `_id, openid, phone, nickname, avatar, role(student/doctor), hospital_id, verify_status(pending/rejected/verified), credit_score, stats{published, accepted, completed}` | 用户档案，hospital_id 为隔离锚点 |
| `dealings` | `_id, type(requirement/service), hospital_id, owner_uid, category(shift/case_guide/resume_guide), title, detail, schedule, fee, status, accepted_uid, accept_deadline, created_at` | 撮合单；组合索引 `hospital_id+status+created_at` |
| `applications` | `_id, dealing_id, applicant_uid, message, status(pending/accepted/rejected/cancelled), created_at` | 申请/预约记录；从 dealing 继承医院上下文 |
| `messages` | `_id, dealing_id, conversation_id, from_uid, to_uid, content, msg_type(text), read, created_at` | 站内私信；仅存在于已确认撮合单之下 |
| `reviews` | `_id, dealing_id, from_uid, to_uid, rating(1-5), content, created_at` | 双向互评，completed 后开放 |
| `reports` | `_id, dealing_id, reporter_uid, reason, evidence(fileIDs), status(open/processing/resolved), result` | 举报与仲裁 |

**通用约定**：金额字段为展示性参考价（元，整数分存储均可）；所有集合软删除（`deleted_at`）；`created_at/updated_at` 服务端时间。

## 7. 核心机制设计

### 7.1 站内私信（无 IM 依赖，云开发实现）

- 确认撮合后自动创建会话；**未确认前双方不可互发**（防骚扰、防站外导流）；
- 会话页：进入拉取历史 + `watch` 实时监听新消息；列表页：未读数角标（tabBar badge）；
- 发送前 `msgSecCheck` 过滤；单条长度限制 500 字；
- 量级上来后可平滑迁移腾讯云 IM（扩展 SDK），接口层预留封装。

### 7.2 通知（订阅消息）

关键节点触达：收到申请、申请被确认、履约确认提醒、新私信、举报处理结果。需在对应操作前调用 `wx.requestSubscribeMessage` 征集授权。

### 7.3 实名认证与信用分

- 认证材料存云存储（私有读，fileID 不下发无关用户）；人工审核走简易 admin 云函数 + 后台页（小程序内嵌管理端即可，pilot 阶段不做独立系统）；
- 信用分初始 100；正向：完成互评 +2；负向：被举报成立 −20 / 超时取消 −5；低于阈值限制发布与申请；
- 信用分与履约统计展示在用户名片上（撮合单详情可见对方信用）。

### 7.4 内容安全（提审硬要求）

- 发布文本 `msgSecCheck`、图片 `imgSecCheck`，先审后发；
- 病例类内容输入框强制提示：**禁止患者可识别信息（姓名/ID/影像号），需脱敏后发布**；
- 举报入口全量覆盖（撮合单/私信/用户），举报成立内容下架、账号处置。

## 8. 合规设计要点

| 风险点 | 对策 |
|---|---|
| 二清/资金托管 | 平台零资金流；界面仅提示"酬金请线下与对方直接结清"，**无任何站内支付/收款入口** |
| 医疗合规 | 定位"经验分享/学习交流"，禁止诊疗、开方类内容；免责声明；提示线下就医 |
| 换班院规 | 固定提示语："换班需遵守所在医院相关规定，平台仅提供信息撮合" |
| 导流审核风险 | 联络一律站内私信完成；不展示微信号/手机号明文 |
| 隐私 | 手机号收集需授权 + 隐私政策声明（用户隐私保护指引配置）；认证材料最小化收集 |

正式期若交易化（企业主体 + EDI + 微信分账/电商收付通）路径已在前期调研文档中评估，验证期不实施。

## 9. Pilot 验收方案（长春 3 家吉大医院）

**范围**：吉林大学第一医院、第二医院、中日联谊医院；`hospitals` 预置 3 条 + 每院 5-10 名种子认证用户。

| # | 验收用例 | 预期结果 |
|---|---|---|
| A1 | A 院用户发布换班需求 | A 院列表可见；B/C 院列表不可见 |
| A2 | 伪造请求携带 B 院 hospital_id 读写 | 云函数拒绝（越权防护生效） |
| A3 | B 院用户申请 A 院撮合单 | 拒绝，提示本院限制 |
| B1 | 发布→申请→确认→私信→确认完成→互评 | 3 家医院各完成 ≥1 次全链路闭环 |
| B2 | 未认证用户尝试发布/申请 | 全部拦截，引导去认证 |
| C1 | 订阅消息触达（申请/确认/提醒） | 正常收到 |
| C2 | 违禁内容发布（文本/图片） | 内容安全接口拦截 |
| C3 | 举报→仲裁→下架 | 流程走通，结果回写 |

**验收标准**：以上用例全部通过 + 三院各 ≥5 名真实用户完成至少一次真实撮合。

## 10. MVP 范围与里程碑

tabBar：**首页**（本院列表+搜索+筛选+切换医院浏览）· **发布**（需求单/挂牌服务）· **消息**（会话+私信）· **我的**（认证、我的发布/申请、信用分、评价）

| 阶段 | 周期 | 交付物 |
|---|---|---|
| M1 骨架 | 第 1 周 | 工程初始化、云开发环境、登录+选院+认证流（含 admin 审核） |
| M2 撮合主链路 | 第 2 周 | 双模式发布、列表/搜索/筛选、申请、确认、状态机+超时任务 |
| M3 联络与闭环 | 第 3 周 | 站内私信+订阅消息、确认完成、互评、信用分 |
| M4 收尾提审 | 第 4 周 | 举报仲裁、内容安全全量接入、隐私协议、提审 |

## 12. 开放问题

1. 小程序注册主体：个人（快）vs 企业（正式期必须）；
2. AppID 尚未注册/提供；
3. D6 跨院浏览策略最终确认；
4. 酬金字段展示方式：明文展示 vs 区间（如"50-100 元"）——涉及审核观感，建议区间式；
5. 认证审核人员与 SLA（pilot 阶段谁审、多快审）。
